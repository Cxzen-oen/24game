# 账号体系与排行榜：上云架构方案

> 状态：代码已实现并通过本地接口验证；云服务器待部署（等公网 IP）。
> 对应代码：`demo/server`（Spring Boot）、`demo/web`（Vite + TS）、`compose.prod.yaml`、`Dockerfile`、`deploy/`。
> 规则依据：`docs/24点游戏_单人挑战与排行榜_规则说明.md`。

## 0. 一页结论

- **账号**：Spring Security 6 + JWT（HS256，30 分钟）+ 轮换式 Refresh Token（30 天，仅存 SHA-256，HttpOnly Cookie）。密码 BCrypt cost 12。游客可继续玩，登录/注册时把本机游客成绩自动并入账号；**只有账号成绩进入排行榜**。
- **排行榜**：不另建榜单表，直接由 `personal_bests`（每账号每「模式 × 难度」一条最佳）派生。A 榜按答对数降序、计榜用时升序；B 榜按计榜用时升序；并列按取得时间、再按账号 ID 兜底。附「我的排名」与分页。
- **数据库**：PostgreSQL 16，Flyway 迁移（V1 已有，V2 新增账号/令牌/归属字段/榜单索引）。数据库只在 Docker 内网，不暴露公网；每日 `pg_dump`，保留 14 天，可接对象存储异地备份。
- **部署形态**：一台云服务器 + Docker Compose：Caddy（HTTPS/静态缓存）→ Spring Boot（同时托管前端）→ PostgreSQL。单机足够支撑早期规模，扩容路径已写明。
- **上线前必须确认**：域名与备案、云厂商/地域、是否需要微信/手机号登录、是否接受「账号密码 + 无自助找回」的首版。

## 2. 账号体系

### 2.1 身份模型

两种玩家身份，服务端以 `account_id` 优先：

| 身份 | 标识 | 能否上榜 | 说明 |
|---|---|---|---|
| 游客 | 浏览器生成的 `guest_id`（`X-Guest-Id` 头） | 否 | 打开即玩，成绩存本机对应的游客记录 |
| 账号 | JWT 的 `sub`（账号 UUID） | 是 | 登录后所有新对局直接归账号 |

对局表 `games` 同时保留 `account_id` 与 `guest_id`：

- 游客局：`account_id IS NULL`，按 `guest_id` 鉴权；
- 账号局：`account_id` 非空，按账号鉴权，忽略请求里的 guestId；
- 游客局被账号认领后：`account_id` 写入、`guest_id` 保留用于审计，此后只有该账号能访问。

> 这样既保留「不登录先玩」的转化路径，又保证排行榜只有真实账号，且换设备登录后成绩可恢复。

### 2.2 注册、登录与游客合并

```text
POST /api/auth/register { username, password, nickname, guestId? }
POST /api/auth/login    { username, password, guestId? }
POST /api/auth/refresh  (Cookie: g24_rt)
POST /api/auth/logout   (Cookie: g24_rt)
GET  /api/auth/me       (Authorization: Bearer)
```

注册/登录请求带 `guestId` 时，在**同一个数据库事务**里完成：

1. 创建/读取账号；
2. `UPDATE games SET account_id = ? WHERE guest_id = ? AND account_id IS NULL`；
3. 同样更新 `game_results`；
4. 把游客的 `personal_bests` 按「严格更好才替换」并入账号，再删除游客最佳；
5. 签发令牌。

账号行使用 `SELECT ... FOR UPDATE` 串行化，避免同账号并发合并产生唯一键冲突或最佳成绩互相覆盖。

### 2.3 令牌与会话

| 令牌 | 形式 | 有效期 | 存放 | 用途 |
|---|---|---|---|---|
| Access Token | JWT HS256，含 `sub`、`nick`、`tv`、`jti` | 30 分钟 | 前端内存 + sessionStorage | `Authorization: Bearer` |
| Refresh Token | 32 字节随机串 | 30 天，滑动 | `HttpOnly; SameSite=Strict; Path=/api/auth` Cookie | 只用于换新 access token |

- 数据库只存 refresh token 的 SHA-256，泄露数据库也无法直接登录。
- **每次刷新轮换**：旧令牌标记 `revoked_at` 与 `replaced_by`；旧令牌被重放视为泄露，撤销该账号全部刷新令牌（需重新登录）。
- `accounts.token_version`：封禁、改密时 +1，使已签发但未过期的 JWT 立即失效；每请求校验一次账号状态（主键查询，成本可忽略）。
- 刷新接口与业务接口同源，Cookie 带 `SameSite=Strict`，不需要额外 CSRF token；生产环境 `COOKIE_SECURE=true` 只走 HTTPS。

### 2.4 安全措施（已落地）

| 风险 | 处理 |
|---|---|
| 密码泄露 | BCrypt cost 12，只存哈希 |
| 撞库/爆破 | 单 IP 登录 60 次/10 分钟；同 IP+用户名失败 8 次/15 分钟锁定 |
| 用户名枚举 | 用户名不存在也跑一次 BCrypt；统一返回「用户名或密码错误」 |
| 账号被盗后长期有效 | access 30 分钟，refresh 轮换 + 重放检测 |
| 封禁不生效 | 每请求检查账号状态与 token_version |
| 注册灌水 | 单 IP 每小时 10 个账号（单机内存计数） |
| XSS 偷 token | refresh 为 HttpOnly；昵称在渲染时转义；access 短时效 |
| 数据库暴露 | 生产 Compose 不给 PostgreSQL 映射宿主端口 |

限流目前是**单实例内存**实现；多实例时换 Redis（接口不变），见 5.8。

### 2.5 为什么用 Spring Security

需求是「用户名密码 + 无状态 API + 以后可能接微信」。没有手写鉴权，直接使用 Spring 官方栈：

- `spring-boot-starter-security`：过滤器链、BCrypt、标准 401 响应；
- `spring-boot-starter-oauth2-resource-server` + Nimbus JOSE：JWT 签发/验签/过期校验，不用自己拼 HMAC；
- 以后接微信：加 `spring-security-oauth2-client`，在 `accounts` 旁加 `account_identities(provider, subject)` 即可，无需改动对局与排行榜。

### 2.6 账号扩展位（未实现）

- 微信扫码/公众号登录：需要 AppID、AppSecret、已备案域名与 HTTPS；
- 手机号验证码：需要短信服务商与实名模板；
- 找回密码：需要邮箱或短信通道；
- 昵称审核：先做长度/控制字符校验，敏感词与人工审核后置。

## 3. 排行榜

### 3.1 榜单口径（与规则文档一致）

| 榜单 | 第一比较项 | 第二比较项 | 并列 |
|---|---|---|---|
| A × L1/L2 | 答对题数多 | 第 N 题计榜用时短 | 先取得者优先 |
| B × L1/L2 | 总计榜用时短 | — | 先取得者优先 |

四个榜互相独立；每账号每榜只保留一条最佳，不重复占名次；A 零题不上榜。

### 3.2 数据来源：不建第二份榜单

`personal_bests` 已经是「每账号每榜最佳」，且与结算在同一事务写入。排行榜直接查它，避免「最佳成绩」和「榜单」两份数据不一致：

```sql
SELECT b.account_id, a.nickname, b.best_correct, b.best_scoring_ms, b.achieved_at
  FROM personal_bests b
  JOIN accounts a ON a.id = b.account_id
 WHERE b.account_id IS NOT NULL
   AND b.mode = 'A'::game_mode AND b.level = 'L1'::game_level
   AND a.status = 'ACTIVE'
 ORDER BY b.best_correct DESC, b.best_scoring_ms ASC,
          b.achieved_at ASC, b.account_id ASC
 LIMIT 20 OFFSET 0;
```

### 3.3 索引

```sql
-- 每个账号每个模式×难度只有一条
CREATE UNIQUE INDEX uq_best_account_mode_level
  ON personal_bests (account_id, mode, level) WHERE account_id IS NOT NULL;

-- A 榜读取路径
CREATE INDEX idx_best_board_a
  ON personal_bests (mode, level, best_correct DESC, best_scoring_ms ASC, achieved_at ASC)
  WHERE account_id IS NOT NULL;

-- B 榜读取路径
CREATE INDEX idx_best_board_b
  ON personal_bests (mode, level, best_scoring_ms ASC, achieved_at ASC)
  WHERE account_id IS NOT NULL;
```

### 3.4 我的排名

先读自己的最佳，再数「排在我前面的人」+1。比较条件与 ORDER BY 完全一致（含 achieved_at、account_id 兜底），保证分页名次和「我的排名」不打架。

复杂度是索引范围扫描 + 计数。以 10 万账号/榜估算，单次约几毫秒到十几毫秒；四个榜都是独立的窄索引。

> 展示隐私：排行榜昵称由服务端统一隐藏首字符（如 心算王 → *算王），API 返回时即脱敏，前端不再拿到完整昵称。

### 3.5 性能与扩展

- 当前：Postgres 单表 + 部分索引，读多写少（只有刷新个人最佳时才写）。
- 10 万～50 万账号：仍然够用；给榜单接口加 30～60 秒进程内缓存即可。
- 百万级或高并发：Redis ZSET 做 Top N 缓存（member=accountId，score 用 `答对数 × 10^9 − 计榜毫秒`），Postgres 仍是唯一真相，缓存只读；或定时把前 1000 名落到 `leaderboard_snapshots`。
- 赛季/周榜：加 `season_id` 维度与分区即可，当前未做。

## 4. 数据库

### 4.1 表清单

| 表 | 作用 | 关键约束 |
|---|---|---|
| `accounts` | 账号、昵称、密码哈希、状态、token 版本 | username 唯一（小写）；status ∈ ACTIVE/BANNED |
| `refresh_tokens` | 刷新令牌哈希、轮换链 | token_hash 唯一；account_id 外键级联 |
| `games` | 对局进行态（含题序、计时、罚时、revision） | 账号/游客唯一归属；`(account_id, request_id)` 幂等；`(guest_id, request_id)` 幂等 |
| `game_puzzles` | 单局题目与状态 | `(game_id, sequence_no)` 唯一 |
| `game_actions` | 写请求幂等记录（actionId + 指纹 + 响应） | `(game_id, action_id)` 唯一 |
| `game_results` | 结算成绩 | 每局一条；归属账号或游客 |
| `personal_bests` | 每账号/游客每榜最佳 | 账号部分唯一索引；result_id 唯一 |

### 4.2 V2 迁移做了什么

```text
accounts / refresh_tokens                 新增
games.account_id, game_results.account_id 新增，guest_id 改为可空
personal_bests.account_id                 新增，账号部分唯一索引
榜单索引                                  新增
```

迁移是**向前兼容**的（新列可空、旧数据不动），老版本应用仍可读写；新版本启动时 Flyway 自动执行。

### 4.3 事务边界

| 场景 | 一个事务内完成 |
|---|---|
| 提交/跳题/退出 | 锁对局 → 校验幂等 → 计时判定 → 写状态 → 结算 → 写结果与最佳 |
| 注册/登录 + 合并游客 | 建号/验密 → 锁账号 → 迁移对局/成绩/最佳 → 签发令牌 |
| 刷新令牌 | 锁令牌行 → 校验 → 旋转 → 写新令牌 |

关键一致性：`game_results` 与 `personal_bests` 同事务；最佳更新用 `INSERT ... ON CONFLICT ... WHERE 新成绩严格更好` 原子完成，不做「先查再写」。

### 4.4 迁移、备份与回滚

- Flyway 只做向前迁移，禁止改历史脚本；
- **发布前先备份**（`deploy/deploy.sh` 已内置）；
- 单机发布允许 10～20 秒不可用；需要零停机时再做双实例滚动；
- 破坏性迁移用 expand-contract：先加列/双写，再切读，最后删旧列（跨两个版本）。

### 4.5 容量与归档

按 1 万账号、人均 30 局/年估算：

| 表 | 年增量 | 说明 |
|---|---|---|
| `game_results` | ~30 万行 | 每局一行，很小 |
| `game_puzzles` | ~300 万行 | 每题一行 |
| `game_actions` | ~600 万行 | 含 JSONB 响应，是最先膨胀的表 |

- 1～3 年内 60GB 磁盘足够；`game_actions` 建议加保留策略（已结算对局的动作保留 90 天），后续用定时任务清理；
- PostgreSQL 默认 autovacuum 够用；大表清理后观察膨胀再调参数；
- 连接池每实例 10，PG `max_connections` 默认 100，最多约 6 个应用实例。

## 5. 上云架构

### 5.1 拓扑

```text
                 手机 / 浏览器
                      │ HTTPS 443
                      ▼
        ┌─────────────────────────────┐
        │ Caddy 2（容器，唯一公网入口）│
        │ TLS 自动续期 / gzip / 缓存   │
        └──────────────┬──────────────┘
                       │ 内网 8080
                       ▼
        ┌─────────────────────────────┐
        │ Spring Boot 3（容器）        │
        │ · 账号/JWT/限流              │
        │ · 对局、判题、计时、结算      │
        │ · 排行榜查询                 │
        │ · 托管前端静态文件            │
        └──────────────┬──────────────┘
                       │ 内网 5432（不映射宿主）
                       ▼
        ┌─────────────────────────────┐
        │ PostgreSQL 16（容器 + 卷）   │
        │ 数据目录 /var/lib/postgresql │
        └──────────────┬──────────────┘
                       │ 每日 03:00 pg_dump
                       ▼
              本机 backups/（14 天）
                       │ 可选 rclone
                       ▼
              对象存储（异地，建议开）
```

### 5.2 组件与规格（首版）

| 组件 | 选型 | 规格建议 | 说明 |
|---|---|---|---|
| 云服务器 | 2 vCPU / 2 GB（小规模测试）/ 4 GB（正式） | 2G 约几十并发、几百 DAU | 带宽 3～5 Mbps |
| 反向代理 | Caddy 2 | 容器 | 自动 HTTPS、HTTP/2、gzip |
| 应用 | Spring Boot 3 + JRE 21 | 单实例 | 同时托管前端构建产物 |
| 数据库 | PostgreSQL 16 | 同机容器，shared_buffers 128MB | 数据卷持久化，不暴露公网 |
| 备份 | pg_dump + cron | 本机 + 可选对象存储 | 保留 14 天 |
| 监控 | 云监控 + `/api/health` 探活 | — | 磁盘、内存、5xx、备份是否成功 |

> 不引入 Kubernetes、消息队列、微服务：当前只有一个业务进程和一张核心表，拆开只会增加故障面。等出现明确瓶颈再按 5.8 演进。

> 2C2G 部署时：JVM 堆 512MB、Postgres shared_buffers 128MB、容器内存上限见 compose.prod.yaml；另配 2GB swap。构建不要在 2G 服务器上跑，改为本地构建 jar + 轻量 runtime 镜像（deploy/build-local.ps1 + deploy/Dockerfile.runtime）。

### 5.3 网络与端口

| 端口 | 暴露 | 用途 |
|---|---|---|
| 22 | 仅你的固定 IP（最好只开密钥登录） | SSH |
| 80 | 公网 | HTTP，Caddy 跳转/签发证书 |
| 443 | 公网 | HTTPS |
| 8080 / 5432 | **不暴露** | 只在 Compose 内网 |

云厂商安全组与主机防火墙（ufw）两处都要配，只放行 22/80/443。

### 5.4 域名、HTTPS 与备案（关键）

- Caddy 自动 HTTPS 需要**域名**解析到服务器；只有公网 IP 时只能走 `http://IP`，浏览器不会给 IP 签发受信任证书。
- **中国大陆服务器**：域名解析到大陆 IP 并提供 80/443 服务，通常要求完成 **ICP 备案**；未备案会被云厂商拦截。IP + 高端口（如 `http://IP:8080`）可临时调试，但不适合正式上线。
- 可选：香港/海外服务器免备案，代价是大陆访问延迟略高。
- 微信登录/公众号/小程序要求 HTTPS + 已备案域名 + 域名白名单，这也是账号体系下一阶段的前置条件。

**因此部署前需要你提供：域名（或明确先用 IP:端口 调试）、服务器地域、是否已备案。**

### 5.5 数据持久化与备份

- PostgreSQL 数据在 Docker 命名卷 `pgdata`，容器重建不丢；
- 每日 03:00 `pg_dump -Fc` → `backups/game24-*.dump.gz`，保留 14 天（`deploy/backup.sh`）；
- 建议再加一步 `rclone` 到对象存储，防「服务器整机丢失」；脚本里已留一行开关；
- 恢复：`deploy/restore.sh backups/xxx.dump.gz`，停应用 → `pg_restore --clean --if-exists` → 起应用；
- 每季度做一次恢复演练；备份文件本身要确认非空、可解压；
- 重要变更（迁移、升级）前额外手动备份一次。

RPO ≈ 24 小时（若加对象存储每日同步仍是 24 小时）；需要更小 RPO 时开启云盘快照（如每天一次）或 WAL 归档。

### 5.6 发布与回滚

首版流程（单机）：

```bash
# 服务器上
cd /opt/game24
./deploy/deploy.sh        # 自动先备份，再 docker compose up -d --build
```

- 构建在服务器上进行（多阶段 Dockerfile，2C4G 约 5～8 分钟）；也可以在本地构建后推镜像仓库，减少服务器压力；
- 应用启动时 Flyway 自动迁移；
- 回滚：代码回退 + `APP_TAG` 指向旧镜像重建；数据库迁移不可自动回退，破坏性变更必须靠备份恢复；
- 建议发布窗口避开高峰，发布后检查 `/api/health`、注册登录、榜单三条链路。

### 5.7 监控与日志

- 探活：每分钟请求 `https://域名/api/health`，要求 200 且 `db=UP`；
- 云监控：CPU、内存、磁盘（80% 告警）、带宽；
- 日志：Docker `json-file` 已限制 10～20MB × 5，避免磁盘被日志打满；应用日志输出到 stdout；
- 备份任务成功/失败写日志，建议加一条「超过 26 小时没有新备份」的告警；
- 安全：fail2ban 防 SSH 爆破，unattended-upgrades 自动打系统补丁。

### 5.8 扩容路线

| 阶段 | 触发 | 动作 |
|---|---|---|
| 1. 纵向扩容 | CPU/内存持续 > 70% | 升到 4C8G，几乎不用改代码 |
| 2. 加 Redis | 多实例、限流需共享、榜单 QPS 高 | 限流/令牌缓存/榜单 ZSET；Postgres 仍是真相 |
| 3. 应用双实例 | 单机重启不可接受 | Caddy 负载均衡两个 app 容器，会话无状态已满足 |
| 4. 数据库独立 | 数据量与备份窗口变大 | 换云数据库 PostgreSQL（RDS），改 `DB_URL` 即可 |
| 5. 读扩展 | 榜单读压力大 | 只读副本/缓存/定时快照 |

## 6. 拿到公网 IP 后的上线顺序

1. 你提供：公网 IP、SSH 端口与登录方式、域名（可后补）、云厂商/地域；
2. 初始化服务器：创建 deploy 用户、密钥登录、ufw、fail2ban、Docker；
3. 上传代码（`docs/上云部署手册.md` 有打包命令），配置 `.env.prod`；
4. `./deploy/deploy.sh` 构建并启动；
5. 验证：`/api/health`、注册、登录、游客合并、四个榜单、刷新页面恢复对局；
6. 配置域名解析与 HTTPS（有域名时）；
7. 配置每日备份 cron，做一次恢复演练；
8. 交付访问地址与运维命令。

## 7. 需要你确认的 6 件事

| # | 决策 | 默认建议 |
|---|---|---|
| 1 | 域名与备案 | 有域名且已备案 → Caddy 自动 HTTPS；没有 → 先 IP:8080 HTTP 调试 |
| 2 | 云厂商/地域 | 大陆（需备案）或香港（免备案），2C4G 起 |
| 3 | 登录方式 | 首版用户名+密码；微信/手机号下一阶段 |
| 4 | 找回密码 | 首版无自助找回；可先由管理员后台重置，或接短信/邮箱 |
| 5 | 排行榜周期 | 首版永久榜；周榜/赛季后续加 `season_id` |
| 6 | 防作弊强度 | 见第 8 节，建议至少加「异常速度标记」 |

## 8. 微信小程序路线

如果要上微信小程序，现有 Spring Boot 后端可以保留，但前端需要重写，并补微信登录与 Header 令牌模式；资质、备案、域名与类目要求见 [微信小程序上线准备清单](微信小程序上线准备清单.md)。

## 9. 已知缺口与风险

1. **没有找回密码**：忘记密码目前只能改库重置。正式对外前建议补短信/邮箱或管理员重置入口。
2. **没有防作弊判定**：判题、计时、结算都在服务端，但「解题速度」无法验证。脚本可以在几百毫秒内打完 B 榜 10 题（本地压测即复现）。建议上线前加：
   - 每道题从发题到提交的最小耗时（例如 < 800ms 记为可疑）；
   - 结算时写 `suspicious` 标记，榜单默认排除并留人工复核；
   - 提交接口按账号限速（如 3 次/秒）。
3. **限流是单机内存**：重启清零、多实例不共享；上多实例前换 Redis。
4. **昵称无敏感词审核**：前端已转义，但不能防不当内容；需要审核或词库。
5. **没有管理员后台**：封禁、改密、删成绩目前用 SQL，后续补最小管理页。
6. **备份未自动异地**：脚本留了 rclone 钩子，需要对象存储账号才能开启。
7. **HTTPS 未实测**：本地没有域名，Caddy 配置与证书签发要等域名解析后才能验证。
