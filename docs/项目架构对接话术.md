# 24 点项目架构对接话术

> 用途：导师让你向学院、科研团队、运维或下一个接手人介绍架构时，直接照着说。
> 原则：**不夸大、不隐瞒边界、先讲业务再讲技术、先讲现状再讲演进。**

## 0. 先记住三句话

1. **单体优先，不是微服务。** 当前只有一个 Spring Boot 应用和一个 PostgreSQL，拆微服务只会增加运维和一致性成本。
2. **服务端权威。** 判题、计时、罚时、结算、排行榜都在后端完成，前端只负责展示和采集点击。
3. **数据库同机是当前阶段的选择，不是架构限制。** 以后要隔离或多实例，改一个 DB_URL 就能拆出去。

## 1. 30 秒版（对导师、非技术负责人）

> 这是一个 24 点在线练习和排行榜系统。前端是 Vite + TypeScript 的单页应用，后端是 Spring Boot 单体 API，数据库用 PostgreSQL。
>
> 判题、计时、罚时和结算全部在服务端完成，前端改不了成绩。账号用 JWT 登录，排行榜按 A/B 两种模式、L1/L2 两个难度分成四个榜。
>
> 现在部署在一台 2C2G 的 Ubuntu 服务器上，用 systemd 直接跑 jar，数据库同机，每天自动备份。以后人数上来，可以把数据库拆出去、加负载均衡，应用代码不用改。

## 2. 3 分钟版（对技术对接人）

> 整体分三层。
>
> **第一层是浏览器端**：Vite + TypeScript 写的单页应用，负责选模式、点牌、显示倒计时和榜单。前端不做判题，也不保存成绩，只把每一步操作发给后端。
>
> **第二层是 Spring Boot 单体**：对外提供 REST JSON API，内部分四块——账号与 JWT、对局与规则、题池、排行榜。所有写操作都在事务里，对局进行态也落库，所以刷新页面能恢复原局。
>
> **第三层是 PostgreSQL**：存账号、对局、题目、操作幂等记录、成绩和每个账号的最佳成绩。排行榜不单独建表，直接从最佳成绩表派生，避免两份数据不一致。
>
> 部署上，当前是一台 Ubuntu 22.04、2C2G 的服务器，Java 21 + systemd 跑 jar，PostgreSQL 14 同机，端口 8081，没有 Docker，也没有上 HTTPS。每天 03:00 用 pg_dump 备份，保留 14 天。
>
> 这套东西的特点是：**无状态应用、服务端权威、单库事务**。以后要扩容，应用可以多开实例，数据库可以换 RDS，前面加 Nginx/Caddy，代码不用动。

## 4. 关键设计怎么解释

### 为什么用单体，不拆微服务？

> 现在只有一个业务应用、一个数据库，团队规模也小。拆微服务会带来服务发现、网络调用、分布式事务、链路追踪这些额外成本，对 24 点这个体量没有必要。等出现“某一块需要独立扩容”的真实需求，再按账号、对局、排行榜拆，不提前拆。

### 为什么判题一定要在服务端？

> 前端传的是三步合并操作树，不是最终答案。后端用有理数精确重算，校验四个数字各用一次、算符合法、没有除零，最后判断是否等于 24。前端就算改 JS，也改不了成绩和计时。

### 为什么用 JWT，不直接存 session？

> 应用是无状态的，方便以后多开实例和加负载均衡。Access Token 30 分钟，Refresh Token 30 天、只存哈希、每次刷新轮换，旧令牌重放会撤销整个会话。密码用 BCrypt，数据库只存哈希。

### 为什么排行榜不单独建表？

> 每个账号在每个“模式 × 难度”下只有一条最佳成绩，这张表本身就是榜单的数据源。单独再建一张榜单表，容易出现“最佳成绩更新了、榜单没更新”的不一致。现在查询走部分索引，几百到几万账号都是毫秒级。

### 为什么现在数据库同机、也没用 Docker？

> 当前是一台 2C2G 的演示/小规模服务器，同机省内存、省网络、少一个故障点；这台机器本身没有 Docker，用 systemd 跑 jar 更轻。仓库里其实已经准备了 Dockerfile 和 compose，换到新服务器可以按需切换，不是架构绑死。

## 5. 现状与边界（要主动说，别等人问）

### 已经有的

- 游客试玩、注册登录、游客成绩并入账号；
- A/B × L1/L2 四个排行榜、我的排名、成绩历史筛选；
- 服务端判题、计时、罚时、幂等提交、刷新恢复；
- PostgreSQL 持久化、Flyway 版本化迁移；
- 每日备份、systemd 守护、健康检查。

### 当前环境的真实情况

- 服务器：121.43.236.209，Ubuntu 22.04，2C/1.6G + 4G swap；
- 部署：原生 systemd，端口 8081，**没有 Docker**；
- **没有域名和 HTTPS**，现在是 HTTP 测试环境；
- 数据库同机，只监听 127.0.0.1；
- 2C2G 只适合小规模测试，500 人同时在线需要升级到 4C8G 起。

### 还没做的

- 微信小程序 / 微信登录；
- 找回密码、手机号登录；
- 防作弊判定（服务端能保证判题正确，但保证不了“人类速度”）；
- 管理后台（封禁、重置密码目前改库）；
- 多实例、Redis、负载均衡；
- HTTPS、域名、ICP 备案。

## 6. 对接时请对方确认的 8 件事

1. 服务器规格、数量、操作系统、是否给 root/sudo；
2. 域名、是否已备案、谁来配 HTTPS；
3. 是否允许装 Docker，还是只能原生部署；
4. 数据库同机、独立服务器，还是云 RDS；
5. 安全组/防火墙放行哪些端口；
6. 备份、监控、告警由谁负责；
7. 上线时间、验收标准、是否要压测；
8. 代码、数据库、服务器账号如何交接。

## 7. 常见问题话术

**问：500 人并发能扛吗？**

> 2C2G 不行。500 人同时在线建议 4C8G 起步，500 QPS 或 500 人同时提交需要多实例 + 独立数据库 + Redis。具体要压测，不能只看配置拍脑袋。

**问：为什么不用 Docker？**

> 当前服务器没有 Docker，2G 内存也不划算；原生 systemd 更轻、更好排查。仓库里有 Dockerfile 和 compose，换到有 Docker 的新服务器可以切，部署方式不影响代码。

**问：数据库为什么不独立？**

> 现在数据量小、查询简单，同机延迟最低、运维最少。等应用和数据库抢 CPU、要做多实例或独立备份时再拆，改 DB_URL 就行，代码不用动。

**问：数据安全吗？**

> 密码 BCrypt 哈希、JWT 短时效 + 刷新轮换、数据库不暴露公网、每日备份。当前缺 HTTPS，正式环境要补域名和证书。

**问：怎么迁移到新服务器？**

> 装 Java 21 + PostgreSQL，拷 jar 和 env，pg_dump/pg_restore，起 systemd 服务；或者用仓库里的 Docker compose。数据库迁移和代码迁移是分开的。

**问：为什么不做微服务/Redis？**

> 没有到需要的量级。微服务和 Redis 会带来额外的部署、监控和一致性成本；等有明确瓶颈再上，不用为了技术栈好看提前上。

## 9. 不要说的话

- 不要说“已经支持 500 并发”——没有压测过；
- 不要说“已经上了 HTTPS/防作弊/找回密码”——还没做；
- 不要把 2C2G 演示环境说成生产环境；
- 不要在对接群里发服务器密码、JWT 密钥、数据库密码；
- 不要承诺“以后不用改代码就能无限扩容”——扩容需要架构调整，只是当前代码留了余地。
